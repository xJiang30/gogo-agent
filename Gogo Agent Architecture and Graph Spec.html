1. 总体目标

系统只把需要并行研究、跨领域合成、明确重排的任务放进 graph。普通对话、追问、轻量咨询和 proposal 执行都留在 graph 外，由 TravelAdvisor 和 application services 编排。

TripPlanningGraphV2 是唯一复杂规划 graph，负责 initial_plan、regenerate_recommendations 和已有 trip 上的 day_replan / cross_day_replan / full_replan proposal 生成。

一句话：用户只面对一个 LLM 输入窗口；TravelAdvisor 自主判断走轻量咨询还是明确重排；LightweightFlows 可以直接回答或调用 specialist context，但不能修改 trip；graph 只负责复杂规划和明确重排；正式行程修改必须先生成 TripProposal。

2. 核心决策

One Graph Only

只保留一个复杂规划 graph，避免多 graph / 多 agent runtime 重叠。

Minimal Nodes

graph 保持 skeleton、三类 research、barrier、candidate merge、recommendation planner、validate、finalize 等必要节点。

Proposal First

任何正式 Trip State 修改都必须先产出 TripProposal，等待用户确认。

Error as Semantics

provider 错误翻译为 ResearchOutcome、GraphErrorEnvelope、AdvisorFallbackDecision。

3. 职责边界

对象负责不负责Python 状态
TravelAdvisor总入口、总质量把关、追问/路由结果汇总、graph 结果转译、fallback、proposal execution。不直接做 specialist research，也不把所有 replan 细分规则写在自己内部。已落地 backend/agent/travel_advisor.py，兼容 JS 版 replace_hotel / replace_node / replace_transport intent，支持 camelCase 输入标准化，并消费 ClarificationPolicy、ReplanIntentRouter、SpecialistSelector 的结构化结论。
ClarificationPolicy在 graph 前用 LLM 判断初始规划信息是否足够；信息不足时返回固定格式追问。不生成正式行程，不进入 graph，不执行 proposal。已落地 backend/agent/clarification_policy.py；优先调用 provider 的 generate_clarification_decision，并用 ClarificationDecision schema 校验；模型失败时才 fallback 到最小安全追问。
ReplanIntentRouter判断用户这句话属于 initial_plan、discussion_turn、local_node_proposal、day_replan、cross_day_replan、regenerate_recommendations 还是 lightweight_research。不生成行程，不查 API；只做路由判断。已落地 backend/agent/replan_intent_router.py；优先调用 provider 的 generate_replan_routing_decision，并用 ReplanRoutingDecision schema 校验；模型失败时才走最小规则 fallback。
SpecialistSelector判断这次请求需要 stay、mobility、experience、weather、ticket、flight、rail、price 哪些专业能力。不把 API 拆成 graph node，不直接执行 proposal。已落地 backend/agent/specialist_selector.py；优先调用 provider 的 generate_specialist_selection，并用 SpecialistSelection schema 校验；模型失败时才走最小关键词 fallback。
PlanningBriefBuilder把用户消息和 intent 整理成 PlanningBrief。不做规划生成。已落地 planning_brief_builder.py：优先用 LLM 提取 PlanningBrief；intent_extraction.py 仅做最小安全 fallback，不再规则猜测用户字段，也不默认猜三天。
LightweightFlowsTrip Board consultation layer: direct_answer and contextual_research.Does not enter the complex graph, does not create TripProposal, and does not mutate trip.answer/research use the same real model provider. contextual_research receives current trip, target node, and routing.specialistSelection. Free-text replace/check/compare turns are consultative by default; only explicit replan/edit intent enters graph proposal.
TripPlanningGraphV2复杂规划、研究合并、候选校验、最终输出。不执行 proposal，不负责用户沟通。已落地 initial plan、regenerate_recommendations 复用完整推荐 graph、cross_day_replan LLM proposal 和 graph_error 中断；已有 trip 的 replan 直达 proposal 生成，不再跑 initial research 链路。
ProposalServiceproposal 保存、状态机、history。不重新规划。已落地内存版，并拒绝空 operations proposal。
ApplicationServices创建 run、调用 advisor、返回 run accepted。不直接调用模型。已落地 Python 入口，复用 graph provider，并返回结构化 proposal status 结果。

4. Overall Flow

This version keeps the chat-import entry, but the user no longer sees three candidate recommendation options. The initial chat request enters the full graph, the graph may still compare candidates internally, and TripBoardBuilder converts the selected best plan into one editable TripBoardResponse. After the user enters Trip Board, board changes remain proposal-first.

Graph Flow

Python 当前已实现 initial_plan、graph_error、candidate_merge/recommendation_planner/validate/finalize 主链，并支持 cross_day_replan 由 LLM 生成 TripProposal operations。初始规划中 stay、mobility、experience 三类 research 是真实并行 specialist 分支，全部完成后先进入 research_barrier_node；如果任一分支产生 GraphErrorEnvelope，则 barrier 中断到 graph_error，否则进入 candidate_merge_node，再由 recommendation_planner_node 基于候选上下文生成内部推荐候选，最后由 TripBoardBuilder 选择一个最佳方案并转换成前端可编辑的 TripBoardResponse。用户不再看到三套候选推荐集。cross_day_replan 不再跑 initial research 链路，而是直接定位 affected nodes 并生成 proposal。Python 类名 TripPlanningGraph 对应本文档中的 TripPlanningGraphV2。

9. Proposal 边界

所有正式行程修改都先生成 TripProposal。Python 已复刻内存版 ProposalService 与 ProposalExecutor，支持 pending/conflicted/accepted 等状态与 ReplaceNode / UpdateNode 执行。operations 现在是必填且不能为空；ReplaceNode 必须包含 day_id、node_id、replacement，UpdateNode 必须包含 day_id、node_id、patch。Executor 不再静默跳过无效操作：找不到 day/node、未知操作类型或缺少 payload 时会直接失败，也不会升级 trip version。ReplaceNode 已按 JS runtime 语义执行：保留旧 node，再用 replacement 覆盖字段。后端内部保留 snake_case Pydantic contract，同时在 proposal response 中提供 frontendProposal camelCase 适配，方便现有 JS 页面读取。

10. Provider 与错误上透

QwenResearchProvider 使用 DashScope OpenAI-compatible /chat/completions。它支持这些模型/数据调用：generate_clarification_decision 返回 JSON ClarificationDecision payload，generate_replan_routing_decision 返回 JSON ReplanRoutingDecision payload，generate_specialist_selection 返回 JSON SpecialistSelection payload，generate_planning_brief 返回 JSON PlanningBrief payload，generate_research 返回 JSON research payload，generate_recommendations 返回完整 recommendation JSON，generate_replan_proposal 返回真实 TripProposal operations JSON，generate_local_proposal 返回局部替换 proposal JSON，generate_answer 返回普通文本 answer；另外 get_weather_context 会调用 Open-Meteo 天气 API，为体验节点提供天气上下文。缺配置、HTTP、网络、超时、响应解析错误会包装成 LlmProviderError 或写入 API warnings。

ClarificationPolicy 的 I/O contract：输入是用户原始文本和 intent；优先调用 provider 的 generate_clarification_decision(system_prompt, user_prompt)；输出必须通过 ClarificationDecision Pydantic schema 校验；模型不可用或返回无效 JSON 时使用最小安全 fallback，追问目的地和天数。

ReplanIntentRouter 的 I/O contract：输入是用户原始文本、intent、是否有 current trip；优先调用 provider 的 generate_replan_routing_decision(system_prompt, user_prompt)；输出必须通过 ReplanRoutingDecision Pydantic schema 校验；模型不可用或返回无效 JSON 时使用最小规则 fallback。

SpecialistSelector 的 I/O contract：输入是用户原始文本、route、planning brief；优先调用 provider 的 generate_specialist_selection(system_prompt, user_prompt)；输出必须通过 SpecialistSelection Pydantic schema 校验；模型不可用或返回无效 JSON 时使用最小关键词 fallback。

PlanningBriefBuilder 的 I/O contract：输入是用户原始文本 user_message；优先调用 provider 的 generate_planning_brief(system_prompt, user_prompt)；输出必须通过 PlanningBrief Pydantic schema 校验；成功时写入 builder_source=llm；模型不可用或返回无效 JSON 时使用最小安全 fallback，写入 builder_source=fallback 和 builder_fallback_reason。fallback 仅保留 mode=initial_plan 和 origin_message，不规则猜测目的地、天数、兴趣、预算或偏好。普通问答会使用 discussion_turn brief，本地替换会使用 local_proposal brief，跨天重排会使用 cross_day_replan brief。

LightweightFlows.contextual_research I/O contract: input is current trip, target node, user consultation text, and routing.specialistSelection; it calls provider generate_answer(system_prompt, user_prompt); output must remain an AnswerResponse. It must not generate TripProposal or mutate trip. If the target node type is stay / mobility / experience, TravelAdvisor adds the matching specialist need by default.

recommendation_planner_node 的 I/O contract：输入是 PlanningBrief、skeleton plan 和 candidateContext；输出必须是 3 个完整 TravelPlanRecommendation。planner 失败时返回 graph_error，不再退回占位 recommendation composer。

flowchart LR E["LlmProviderError"] --> P["ProviderFailurePolicy"] --> R["ResearchOutcome"] P --> G["GraphErrorEnvelope"] --> A["AdvisorFallbackDecision"]

Graph 与 Lightweight 分工

LightweightFlows 处理 graph 外的轻量任务：普通问答、轻量研究、local proposal。TripPlanningGraph 处理复杂任务：从零生成 3 个推荐方案、换一组推荐、已有 trip 上的 day/cross-day replan proposal。

local proposal 定义：用户已经有 current trip，并且这次只想替换一个明确节点，例如一个酒店、餐厅、景点或交通块；系统先生成待确认的 TripProposal，不立刻改正式 trip。local proposal 会找到目标 node 和所属 day，再调用 LLM 生成真实 replacement，代码只负责包装成 ReplaceNode operation。

14. Current Implementation Sync

Implemented

  • Initial chat import returns one TripBoardResponse; internal recommendation candidates are not shown as a three-option user choice.
  • TravelAdvisor is the single main agent entry and now enforces: free-text Trip Board turns cannot mutate trip.
  • ReplanIntentRouter routes free-text replace/check/compare to lightweight consultation unless the intent is explicit day/cross-day/full replan.
  • SpecialistSelector still chooses stay/mobility/experience/weather/ticket/price needs; target node type adds the default specialist need.
  • LightweightFlows.answer and LightweightFlows.contextual_research call the real provider through generate_answer and return AnswerResponse only.
  • TripPlanningGraph remains the complex workflow for initial planning, regenerate, and explicit day/cross-day/full replan.
  • Graph replan still returns pending TripProposal; ProposalExecutor mutates trip only after user acceptance.
  • Provider errors are surfaced as structured fallback instead of template output.
  • Python tests cover the new consultation boundary and explicit replan proposal path.

Still To Improve

  • Connect real hotel, map, flight, rail, ticket, and price APIs inside the relevant specialists.
  • Make specialist context richer than the current selection/context prompt.
  • Add HTTP/SSE service wrapper and persistent storage.
