1. 总体目标

系统只把需要并行研究、跨领域合成、明确重排的任务放进 graph。普通对话、追问、轻量咨询和 proposal 执行都留在 graph 外，由 TravelAdvisor 和 application services 编排。

TripPlanningGraphV2 是唯一复杂规划 graph，负责 initial_plan、regenerate_recommendations 和已有 trip 上的 day_replan / cross_day_replan / full_replan proposal 生成。

一句话：用户只面对一个 LLM 输入窗口；TravelAdvisor 自主判断走轻量咨询还是明确重排；LightweightFlows 可以直接回答或调用 specialist context，但不能修改 trip；graph 只负责复杂规划和明确重排；正式行程修改必须先生成 TripProposal。

2. 核心决策

One Graph Only

只保留一个复杂规划 graph，避免多 graph / 多 agent runtime 重叠。

Minimal Nodes

graph 保持 skeleton、三类 research、barrier、candidate merge、recommendation planner、validate、finalize 等必要节点。

Proposal First

任何正式 Trip State 修改都必须先产出 TripProposal，等待用户确认。

Error as Semantics

provider 错误翻译为 ResearchOutcome、GraphErrorEnvelope、AdvisorFallbackDecision。

4. Overall Flow

CurrentTrip Board is the source of truth. The agent does not own hidden itinerary state. Every turn reads the latest board version, selected day/node, and the user message. Board content changes only when the user saves a manual edit, applies a node suggestion, or accepts a graph proposal.

flowchart TD BOARD["CurrentTrip Board version + days + nodes"] --> A["TravelAdvisor main agent entry"] U["User message / selected node"] --> A A --> C["ClarificationPolicy initial planning only"] C -->|needs info| Q["Clarification question"] C -->|ready| R["ReplanIntentRouter route decision"] R --> S["SpecialistSelector CapabilityPlan"] S --> CP["required from node/tag optional from LLM/user input needs = required + optional"] R -->|initial plan / regenerate| G1["TripPlanningGraph"] G1 --> RS["stay / mobility / experience research"] RS --> PL["candidate merge + planner + validator"] PL --> TBB["TripBoardBuilder"] TBB --> BOARD R -->|direct answer / consultation / apply-to-node prep| LWF["LightweightFlows"] CP --> LWF LWF --> ANS["Answer or node suggestion no trip mutation"] ANS --> APPLY["User applies to node"] APPLY --> BOARD R -->|day / cross-day / full replan| G2["TripPlanningGraph.replan"] CP --> G2 G2 --> PROP["TripProposal pending"] PROP --> ACCEPT{"User accepts proposal?"} ACCEPT -->|yes| EXEC["ProposalExecutor"] EXEC --> BOARD ACCEPT -->|no| BOARD

LightweightFlows can use the capability plan to consult specialist context, but it must not mutate trip or create TripProposal. TripPlanningGraph is reserved for initial board generation and explicit day/cross-day/full replan. Replan output stays pending until user acceptance.

Python 当前已实现 initial_plan、graph_error、candidate_merge/recommendation_planner/validate/finalize 主链，并支持 cross_day_replan 由 LLM 生成 TripProposal operations。初始规划中 stay、mobility、experience 三类 research 是真实并行 specialist 分支，全部完成后先进入 research_barrier_node；如果任一分支产生 GraphErrorEnvelope，则 barrier 中断到 graph_error，否则进入 candidate_merge_node，再由 recommendation_planner_node 基于候选上下文生成内部推荐候选，最后由 TripBoardBuilder 选择一个最佳方案并转换成前端可编辑的 TripBoardResponse。用户不再看到三套候选推荐集。cross_day_replan 不再跑 initial research 链路，而是直接定位 affected nodes 并生成 proposal。Python 类名 TripPlanningGraph 对应本文档中的 TripPlanningGraphV2。

9. Proposal 边界

所有正式行程修改都先生成 TripProposal。Python 已复刻内存版 ProposalService 与 ProposalExecutor，支持 pending/conflicted/accepted 等状态与 ReplaceNode / UpdateNode 执行。operations 现在是必填且不能为空；ReplaceNode 必须包含 day_id、node_id、replacement，UpdateNode 必须包含 day_id、node_id、patch。Executor 不再静默跳过无效操作：找不到 day/node、未知操作类型或缺少 payload 时会直接失败，也不会升级 trip version。ReplaceNode 已按 JS runtime 语义执行：保留旧 node，再用 replacement 覆盖字段。后端内部保留 snake_case Pydantic contract，同时在 proposal response 中提供 frontendProposal camelCase 适配，方便现有 JS 页面读取。

ProposalService.persist_proposal 会根据 proposal.base_version 和当前 trip.version 决定状态：版本一致进入 pending，版本不一致进入 conflicted。set_proposal_status 走 try_update_proposal_status，返回结构是 ok、error、proposal，非法迁移时还会返回 from_status 和 to_status。状态 history 记录 from_status、to_status、changed_at。

ProposalExecutor 只允许写入安全节点字段：title、detail、time、location、duration、rationale、notes、area、pace。patch 或 replacement 里的其它字段会被过滤，避免 proposal 越权改写 trip 内部结构。

10. Provider 与错误上透

QwenResearchProvider uses DashScope OpenAI-compatible /chat/completions. Supported calls: generate_clarification_decision, generate_replan_routing_decision, generate_specialist_selection, generate_planning_brief, generate_research, generate_recommendations, generate_replan_proposal, and generate_answer. Structured calls return JSON and are validated by Pydantic schemas; generate_answer returns normal text. get_weather_context uses Open-Meteo for experience weather context. Config, HTTP, network, timeout, and parse errors are wrapped as LlmProviderError or API warnings.

ClarificationPolicy 的 I/O contract：输入是用户原始文本和 intent；优先调用 provider 的 generate_clarification_decision(system_prompt, user_prompt)；输出必须通过 ClarificationDecision Pydantic schema 校验；模型不可用或返回无效 JSON 时使用最小安全 fallback，追问目的地和天数。

ReplanIntentRouter 的 I/O contract：输入是用户原始文本、intent、是否有 current trip；优先调用 provider 的 generate_replan_routing_decision(system_prompt, user_prompt)；输出必须通过 ReplanRoutingDecision Pydantic schema 校验；模型不可用或返回无效 JSON 时使用最小规则 fallback。

SpecialistSelector 的 I/O contract：输入是用户原始文本、route、planning brief；优先调用 provider 的 generate_specialist_selection(system_prompt, user_prompt)；输出必须通过 SpecialistSelection Pydantic schema 校验；模型不可用或返回无效 JSON 时使用最小关键词 fallback。

PlanningBriefBuilder I/O contract: input is raw user_message; it prefers provider generate_planning_brief(system_prompt, user_prompt); output is validated by PlanningBrief. Successful LLM extraction sets builder_source=llm; model/config/JSON failures use safe fallback with builder_source=fallback and builder_fallback_reason. Direct answers, node consultation, and apply-to-node preparation use discussion_turn brief; cross-day replan uses cross_day_replan brief.

LightweightFlows.contextual_research I/O contract: input is current trip, target node, user consultation text, and routing.specialistSelection; it calls provider generate_answer(system_prompt, user_prompt); output must remain an AnswerResponse. It must not generate TripProposal or mutate trip. If the target node type is stay / mobility / experience, TravelAdvisor adds the matching specialist need by default.

recommendation_planner_node 的 I/O contract：输入是 PlanningBrief、skeleton plan 和 candidateContext；输出必须是 3 个完整 TravelPlanRecommendation。planner 失败时返回 graph_error，不再退回占位 recommendation composer。

flowchart LR E["LlmProviderError"] --> P["ProviderFailurePolicy"] --> R["ResearchOutcome"] P --> G["GraphErrorEnvelope"] --> A["AdvisorFallbackDecision"]

10.2 CapabilityPlan Contract

SpecialistSelection now acts as the capability plan. Fields: required are deterministic minimum capabilities from selected node type or tags; optional are LLM/fallback capabilities inferred from user text; needs is the de-duplicated union for compatibility; reasons explains selection; execution_mode is usually lightweight unless explicit graph replan is requested.

{
  "required": ["stay"],
  "optional": ["weather", "mobility"],
  "needs": ["stay", "weather", "mobility"],
  "reasons": ["Target node type defaults to stay specialist"],
  "execution_mode": "lightweight"
}

11. Application Services

backend/application/agent_application_services.py 已复刻 JS 版 application service 的主要入口：start_initial_plan_run(command)、handle_discussion_turn(command)、execute_proposal(command)、set_proposal_status(proposal_id, status)。其中 set_proposal_status 返回结构化结果：成功时 { ok: true, error: null, proposal }；proposal 不存在时 error=proposal_not_found；状态不允许迁移时 error=invalid_status_transition，并带 from_status / to_status。

12. 状态与持久化边界

  • Graph state 是单次运行状态，不等同正式 Trip State。
  • RecommendationSet 是内部规划候选，不直接写正式行程。
  • TripBoard 是当前用户可编辑的事实来源；手动编辑或应用节点建议会直接改变 Board，后端下一轮只读取最新 Board。
  • TripProposal 是 graph 重排修改正式行程前的 pending 对象，必须由用户接受后才能执行。
  • ProposalService 当前是内存实现，保存 proposal 和 status history；history 条目字段是 from_status、to_status、changed_at，后续可替换为真实数据库。

Graph 与 Lightweight 分工

LightweightFlows 处理 graph 外的轻量任务：普通问答、轻量研究、node consultation。TripPlanningGraph 处理复杂任务：从零生成 3 个推荐方案、换一组推荐、已有 trip 上的 day/cross-day replan proposal。

Node consultation / apply-to-node definition: when a current trip and target node exist, LightweightFlows can generate contextual content for that node. It does not create TripProposal and does not mutate the official trip. A node changes only after the user explicitly applies the suggestion.

ProposalService 负责保存和管理 proposal 状态；ProposalExecutor 负责真正修改 trip。执行前必须满足 proposal 已 accepted、operations 存在、trip.version 等于 proposal.base_version、operation 合法、day/node 存在；执行成功后才升级 trip version。状态 history 字段是 from_status、to_status、changed_at。执行结果包含新 trip 和 decisionLog，其中记录 proposalId、tripId、executedAt、operations。

Executor 白名单字段：title、detail、time、location、duration、rationale、notes、area、pace。这意味着 LLM proposal 不能通过 patch/replacement 改写任意内部字段。

14. Current Implementation Sync

Implemented

  • Initial chat import returns one TripBoardResponse; internal recommendation candidates are not shown as a three-option user choice.
  • TravelAdvisor is the single main agent entry and now enforces: free-text Trip Board turns cannot mutate trip.
  • ReplanIntentRouter routes free-text replace/check/compare to lightweight consultation unless the intent is explicit day/cross-day/full replan.
  • SpecialistSelector now produces a capability plan: node/tag capabilities go to required, user-message capabilities go to optional, and needs remains the compatibility union.
  • LightweightFlows.answer and LightweightFlows.contextual_research call the real provider through generate_answer and return AnswerResponse only.
  • TripPlanningGraph remains the complex workflow for initial planning, regenerate, and explicit day/cross-day/full replan.
  • Graph replan still returns pending TripProposal; ProposalExecutor mutates trip only after user acceptance.
  • Provider errors are surfaced as structured fallback instead of template output.
  • Python tests cover the new consultation boundary and explicit replan proposal path.

Still To Improve

  • Connect real hotel, map, flight, rail, ticket, and price APIs inside the relevant specialists.
  • Use CapabilityPlan to call real specialist APIs/skills, not just pass selected needs into a prompt.
  • Add HTTP/SSE service wrapper and persistent storage.
